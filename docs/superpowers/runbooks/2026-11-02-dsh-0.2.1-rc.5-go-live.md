**Owner:** the operator. This document is the operator's: every step below acts on the
operator's harness home `~/.dsh`, or on a copy of it, by hand. The face code never touches HOME
on its own; the one tool that reads a home it was not started on, `face/scripts/check-home.ts`,

**The home today** is a 0.2.0 home: live on 0.2.0-rc.2 since 2026-10-01, session format v4, the
D2 model row present, the link farm deleted (D13), the backup of that move

## §1 Preconditions

   installed it — so stop it with its own command **before** that checkout is merged or
   reinstalled, or a crash restart boots the new code on the un-backed-up home:

   ```bash
   cd "$REPO/face" && npm run service -- status   # launchd's state and pid

   ```

   other face (a terminal `npm start`, a drill face) and every dsh CLI process, and check:


## §2 Backup

```bash
du -sh ~/.dsh                                                    # the space the copy needs, three times over (§2, §3, §7 A)
BAK=~/.dsh.bak-pre-0.2.1-$(date +%Y%m%d)                         # §6 and §7 C use it: set it again in a new shell (the date it was taken)
test -e "$BAK" && echo "$BAK exists: rename or remove it first"  # cp -a into an existing directory nests the copy
cp -a ~/.dsh "$BAK"
diff -rq ~/.dsh "$BAK"                                           # expect no output
ls -l "$BAK/.credentials.yaml"                                   # expect -rw-------
```

- `cp -a` keeps modes (`.credentials.yaml` stays `0600`, as does `.env` if the service wrote one),
  times, and symlinks as symlinks.
- **No link farm this time**: `profiles/node_modules` was deleted at the 0.2.0 move (D13; the
  dry run says `Link farm (D13): profiles/node_modules absent`), so `diff` needs no
  `-x node_modules`. If the dry run finds one again, something 0.1.1 ran on the home — stop.
- rc.5 keeps its own state nowhere else (the same dsh-base path-bearing rows as at 0.2.0, spec
  §9 row 17); the face's own state — the desk's ledger and standing orders under
  `$DSH_HOME/face/`, the service's logs — is inside the home and inside the backup.
- **This is the only way back** (D26, §6). It is stale the moment anything runs on `~/.dsh` again;
  §7 C.1 re-takes it (or diffs it) immediately before the first live boot. Keep the older
  `~/.dsh.bak-pre-0.2.0-20261001` as it is: it is the 0.1.1 home, not this one.

## §4 Decisions to make first

### The credentials precedence (required: compare before the first boot)

rc.5's `@deepseek-ai/dsh-credentials-local` resolves a key in this order — `refs` in
`$DSH_HOME/.credentials.yaml`, then the launch environment, then `<cwd>/.env`, then
`$DSH_HOME/.env` (its `lib/index.js` header; `dsh/README.md` step 3; spec §9 row 20). At 0.2.0
the launch environment came first. So if the home stores a `DEEPSEEK_API_KEY` ref **and** the face
is started with `.env.deepseek` sourced (a terminal `npm start`) or from `$DSH_HOME/.env` (the
service, README "Keys"), the stored ref now wins, silently. List where the name lives — **names
only**: a `refs` entry is one line, `NAME: value`, so a bare `grep` prints the key; the `cut`
keeps the line number and the name (`cut -s` prints nothing for a line without `=`):

```bash
ls -l ~/.dsh/.credentials.yaml ~/.dsh/.env "$REPO/face/.env"     # each that exists: -rw-------; face/.env is <cwd>/.env, expect none
grep -n 'DEEPSEEK' ~/.dsh/.credentials.yaml | cut -d: -f1,2       # e.g. "4:  DEEPSEEK_API_KEY", or nothing
grep -n '^DEEPSEEK' ~/.dsh/.env | cut -s -d= -f1                  # the service's copy, if any
grep -n 'DEEPSEEK' "$REPO/.env.deepseek" | cut -s -d= -f1         # the terminal's copy
```

One name in more than one place: keep one copy, and delete the others — which one is the
operator's choice. To drop the stored ref, open `~/.dsh/.credentials.yaml` in an editor and delete
that one line under `refs:` (keep `version: 1` and the `records:` section with
`client-connection/browser-session`), then `ls -l` it: still `-rw-------`. To keep the stored one
instead, stop sourcing `.env.deepseek` for the face and delete the name from `~/.dsh/.env`.
Whatever stays must hold the key you mean to bill: the agent panel says `set · <source>` (§7 A).

### D12 again - the global CLI

`~/.local/bin/dsh` is 0.2.0-rc.2, installed 2026-10-01 and never run on the home (guide §1). Read

- **Isolate it**: give it its own home (`DSH_HOME=~/.dsh-cli dsh …`).
- **Stop using it** on this home (`npm rm -g @deepseek-ai/dsh`, or leave it unrun).

## §6 Rollback: a full restore, never one session — and lossy (D26)

```bash
cd "$REPO/face" && npm run service -- stop        # or stop the terminal face; then §1's checks
echo "$BAK"                                       # still set from §2? else: BAK=~/.dsh.bak-pre-0.2.1-<the date it was taken>
test -d "$BAK" && mv ~/.dsh ~/.dsh.failed-0.2.1 && cp -a "$BAK" ~/.dsh
diff -rq "$BAK" ~/.dsh                            # expect no output
```

`test -d` first: a wrong `BAK` stops the line before the home is renamed.

- Then run the 0.2.0 face only from a 0.2.0 checkout with its own `node_modules` — the primary at
  the commit before the merge, `npm ci` there, then `npm run service -- start` (the service runs
  that checkout's files) or `npm start`. The rc.5 code on a restored home is a new go-live, not a
  rollback.
- **Lossy.** rc.5's event vocabulary has 62 types where 0.2.0's had 59 (spec §10): every agent
  `bash` call writes `job/registered` and `job/settled`, and 0.2.0 refuses a log carrying a type it
  does not know. So practically every session used under rc.5 is unreadable by 0.2.0, and
  everything done under rc.5 after the backup lives only in `~/.dsh.failed-0.2.1`. A rollback
  keeps the backup's state and loses the rest.
- Never "roll back" one session by deleting or editing its files: the turns taken under rc.5 live
  only in that session's v4 file, and the 0.2.0 reader refuses the whole log, not the new tail.
- The global CLI, if §4 upgraded it to rc.5, is an rc.5 tool: keep it off the restored home.
